# Правила вайрфреймів TheBrain

Складено 2026-10-04. Діють на всі екрани.
Замовлення на перші три — [`_screens.md`](_screens.md).

---

## 1. Деталізація

**Тільки структура, ієрархія і зони.** Вайрфрейм відповідає на питання
«що тут є і що головне», а не «як це виглядає».

| Можна | Не можна |
|---|---|
| Прямокутники, лінії, відступи | Колір — жодного, крім сірого |
| Відтінки сірого для рівнів | Шрифти — тільки системний, одна гарнітура |
| Різна вага тексту для ієрархії | Бренд, логотип, іконки |
| Підпис-заглушка на місці зображення | Справжні картинки й аватари |

**Сіра шкала — чотири рівні, не більше.** Тло, поверхня, межа, текст.
Якщо для пояснення екрана знадобився п'ятий — це ознака, що екран
складніший, ніж має бути.

> **Правило, специфічне для нас.** У §8 брифу статус несе **колір**:
> зелений — вчасно, бурштиновий — сьогодні, червоний — прострочено.
> У вайрфреймі кольору немає, тож статус має читатись **формою, вагою
> або словом**. Якщо без кольору зрозуміти, що горить, неможливо —
> це дефект структури, і його треба побачити саме зараз, а не після
> того, як колір усе замаскує.

## 2. Розмітка

**Семантичний HTML.** Елемент обирається за змістом, не за виглядом.

| Для чого | Елемент |
|---|---|
| Шапка екрана | `<header>` |
| Три пункти глобальної навігації | `<nav>` |
| Вміст екрана | `<main>` |
| Смислова група — «прострочене», «сьогодні» | `<section>` з `<h2>` |
| Самостійна одиниця — крок, клієнт, запис хронології | `<article>` |
| Введення — нотатка, новий клієнт | `<form>`, `<label>`, `<textarea>` |
| Будь-яка дія | `<button>`, не `<div onclick>` |
| Перехід на інший екран | `<a href>` на реальний файл вайрфрейму |
| Список клієнтів чи кроків | `<ul>` / `<li>` |

**Чому це не формальність.** Семантика — це і є структура, яку ми
перевіряємо. Якщо екран не розкладається на `section` і `article`,
значить ієрархія не продумана, і суцільні `div` просто сховають це.

**Доступність іде звідси ж.** Заголовки по порядку, `<button>` фокусується
з клавіатури, у форми є `<label>`. Безкоштовно, якщо робити одразу.

## 3. Текст

**Справжній текст із домену, ніякого lorem ipsum.** Заглушки ховають
реальні проблеми: довгі імена, довгі назви кроків, порожні поля.

**Один набір даних на всі екрани.** Клієнти, що з'являються у вайрфреймах,
— ті самі скрізь: у «Сьогодні», у списку, у картці. Вайрфрейми мають
складатись в одну історію, а не бути набором непов'язаних макетів.

**Робочий набір:**

| Клієнт | Професія фахівця | Що в роботі |
|---|---|---|
| Олена К. | репетитор | Підготовка до іспиту, крок 4 з 8 |
| Марта Д. | репетитор | Розмовний курс, крок 2 з 12 |
| Богдан П. | репетитор | Прострочено на 3 дні |
| Ніна В. | репетитор | Без плану |
| Тарас Л. | репетитор | На паузі |

> **Імена вигадані й мають такими лишатись.** Репозиторій публічний,
> і в `CLAUDE.md` записано: імен реальних клієнтів тут не буває.
> Тільки ініціал прізвища, щоб було видно, як поводиться довге ім'я.

**Мова — українська.** Вона на 10–15% довша за англійську, тож макет,
який тримається в UK, витримає й EN (§9 брифу вимагає обидві).

**Словник домену:** клієнт · план роботи · крок · термін · прострочено
· хронологія · нотатка · фідбек клієнта · пресет · шаблон · перебудувати план.
Не «таски», не «проєкти», не «картки».

## 4. Назви файлів

**Латиницею, малими, через дефіс.** Один екран — одна базова сторінка
плюс по сторінці на кожен стан.

```
wireframes/<екран>.html                 базовий, наповнений стан
wireframes/<екран>-<стан>.html          окремий стан
wireframes/<екран>-<стан>-<варіант>.html  коли станів одного типу кілька
```

**Третій рівень — наше доповнення** до схеми із замовлення. Він потрібен,
бо в нас **порожніх станів буває кілька на один екран**, і вони означають
різні речі: `today-empty-first` і `today-empty-calm` — не одне й те саме.

**Канонічні суфікси станів:** `-loading` · `-empty` · `-error`.
Успіх суфікса не має — це базова сторінка.

**Відповідність українських назв латинським:**

| Екран у sitemap.md | Файл |
|---|---|
| Сьогодні | `today` |
| Список клієнтів | `clients` |
| Клієнт | `client` |
| План клієнта | `plan` |
| Режим «переграти план» | `plan-rebuild` |
| Нотатка після кроку | `note` |
| Новий клієнт | `client-new` |
| Вибір шляху: пресет або з нуля | `path-choice` |
| Мої шаблони | `templates` |
| Загальний таймлайн | `timeline` |
| Тариф і ліміт | `plan-limit` |

## 5. Стани

**Кожен стан — окрема сторінка.** Не перемикач, не параметр.
Сторінку можна відкрити, показати й обговорити окремо.

**Структура однакова, вміст різний.** Шапка, навігація і зони лишаються
на місці; змінюється те, що в них. Якщо для порожнього стану довелося
переробити каркас — або каркас неправильний, або це насправді інший екран.

**Базова сторінка — це успіх.** Окремий файл `-success` заводимо тільки
там, де у flow є екран «вийшло». У головному потоці такого немає
(див. `_screens.md`), у R1 є — підсумок після перебудови.

**Перелік файлів для головного потоку:**

| Файл | Стан | Звідки |
|---|---|---|
| `today.html` | базовий: день із справами | MAIN |
| `today-loading.html` | завантаження | вузол LOAD |
| `today-empty-first.html` | порожньо: клієнтів ще немає | WHY → клієнтів немає |
| `today-empty-gaps.html` | порожньо: N клієнтів без плану | WHY → є клієнти без планів |
| `today-empty-calm.html` | порожньо: усе під контролем | WHY → усе гаразд |
| `today-error.html` | офлайн, кешовані дані з позначкою | вузол STALE |
| `today-overdue.html` | стіна прострочених після паузи | вузол BACK |
| `clients.html` | базовий: список активних | MAIN |
| `clients-empty.html` | пошук нічого не знайшов | вузол NOTFOUND |
| `clients-archived.html` | знятий фільтр, видно завершених | вузол ARCHIVE |
| `client.html` | базовий: крок, хронологія, що попереду | MAIN, **тут закривається головний job** |
| `client-loading.html` | завантаження | вузол CLOAD |
| `client-empty-plan.html` | плану ще немає | вузол NOPLAN |
| `client-empty-history.html` | хронологія порожня | вузол NOHIST |
| `client-error.html` | не вдалося завантажити, повтор | вузол ERROR |
| `client-error-cached.html` | кешована копія з позначкою | вузол CACHED |

**Шістнадцять сторінок.** У `_screens.md` рахувалось 11 станів —
різниця в п'яти варіантах, які flow вимагає окремими екранами:
стіна прострочених, знятий фільтр архіву, і три різні порожнечі
замість однієї.

## 6. Що лишаємо на потім

| Не чіпаємо зараз | Коли |
|---|---|
| Колір, зокрема семантика статусів | Ф3, дизайн-система |
| Шрифти, типографічна шкала | Ф3 |
| Тіні, радіуси, межі як декор | Ф3 |
| Іконки | Ф3 |
| Анімація, переходи | Ф3 |
| Готові компоненти UI | Ф3 |
| Темна тема | Ф3 — обидві теми рівноправні, але після структури |

**Правило перевірки.** Якщо на вайрфреймі виникла суперечка про те,
як щось виглядає, — її треба відкласти. Якщо виникла суперечка про те,
що на екрані головне, — це робота вайрфрейму, і вирішувати треба зараз.

## 7. Правила продукту, що діють на всіх екранах

З [`../sitemap.md`](../sitemap.md) і [`../flows.md`](../flows.md):

- **Правило виходу.** Кожен стан відмови веде кудись. Не завантажилось —
  повтор або кеш. Порожньо — причина плюс дія. На вайрфреймі це означає:
  **на сторінці стану має бути видима кнопка**, не самий лише текст.
- **Правило порожніх станів.** Порожньо = причина плюс наступний крок.
  Порожній екран без пояснення — незакрите замовлення.
- **Глобального CTA немає.** Три пункти навігації: Сьогодні · Клієнти · Шаблони.
- **Головна дія «Сьогодні» живе на рядку**, не на екрані — «закрити крок».
- **Одна головна дія на екран.** Якщо на вайрфреймі їх дві рівноцінні,
  екран не вирішено.
- **R4 як критерій приймання.** «Сьогодні» і «Нотатка» мають читатись
  і закриватись однією рукою за секунди. Перевірка на вайрфреймі: чи
  вміщається головне у верхню третину екрана.
- **Ширина — телефон.** 390 пікселів, iOS. Усе, що не вміщається, —
  привід різати зміст, а не зменшувати шрифт.
